# HTMT 1.0 — HyperText Markup Transcript

**Design document · 2026-09-01 · Status: approved for implementation planning**

---

## 1. Problem and thesis

A recorded meeting is a large, opaque artifact. A one-hour screen-share is ~1 GB, and
the parts that matter — the moments where someone says *"look at this"* and points at
a chart, a dashboard, a line of code — are unfindable without watching it. Transcripts
solve the searchability problem but throw away everything visual: the transcript says
"look at this chart", and the chart is gone.

HTMT is a file format that keeps both. It stores the conversation as structured,
timed, semantically annotated text, and it stores **the frames that were being pointed
at, at the moments they were pointed at** — nothing else from the video. The result is
a single file that a browser opens natively, that a person can read top to bottom, and
that costs one to two megabytes instead of a gigabyte.

The production path is an AI pipeline: a language model reads the transcript to find
where deixis ("this", "here", "as you can see") implies something is being shown, and
a vision pass looks at candidate frames to confirm something actually *is* being shown
before a frame is kept.

> **HTML** describes documents. **HTMT** describes conversations over time, including
> what was on screen when they happened.

### 1.1 Relationship to prior discovery work

`discovery/uploads/htmt-1.0-specification.html` contains an earlier draft that models
HTMT as a standalone XML-like language (`<!HTMT 1.0>`, `<transcript>`, `<turn>`). That
draft's **conversation model is adopted wholesale** — turns as the primary unit,
optional timestamps, the semantic vocabulary, the module system, the graceful-degradation
and security rules. What changes is the substrate: HTMT 1.0 is a strict profile of
HTML5 rather than a new language, and it gains a Vision module the draft did not have.

The draft's own principles argued for this change. "Human-readable without a parser"
and "graceful degradation" are strictly better served by a format every browser on
earth already renders.

## 2. Design decisions

These were settled during brainstorming and are load-bearing for everything below.

| # | Decision | Rationale |
|---|---|---|
| D1 | HTMT is a **profile of HTML5**, not a new language | Browsers render it natively with no viewer, no build step, no XSLT (which Chrome is removing), no MIME negotiation |
| D2 | A **signature convention** replaces the custom doctype | `<!doctype html>` is the only doctype that guarantees standards mode; the HTMT declaration moves to `<html data-htmt="1.0">` plus a machine-sniffable comment |
| D3 | **Still frames are core; clips are optional** | Frames keep files tight enough for single-file portability; clips remain expressible where motion matters |
| D4 | **Transcript + moment deck** reading model | Document reads as a normal article without JS; the embedded script adds a paging deck over the moments |
| D5 | **Native HTML inside custom elements** | Custom elements carry structure; anything that must render without JS (`img`, `a`, `video`, `figure`) is native HTML |
| D6 | Pipeline is **two-stage: text deixis → vision verification** | A text-only pass produces false positives ("*this* quarter was rough" with nothing on screen); vision confirms before a frame ships |
| D7 | Reference implementation is **TypeScript / npm** | One language across viewer, validator, converters, and CLI; `npx htmt` is the lowest-friction distribution |

Approach explicitly rejected: a canonical XML format plus a compiled HTML viewer output
(two artifacts, two specs, and the `.htmt` a user actually receives would not be the
canonical one).

## 3. Format identity

### 3.1 File signature

Every HTMT document begins with exactly this shape:

```html
<!doctype html>
<!-- HTMT/1.0 mode=single-file moments=12 duration=00:47:19 -->
<html lang="en" data-htmt="1.0">
```

- Line 1 is the HTML5 doctype. **Required**, verbatim. This is what makes browsers
  render the file in standards mode.
- Line 2 is the **HTMT signature comment**. Recommended, and emitted by all reference
  tooling. It exists so that `file(1)`-style sniffing, indexers, and streaming parsers
  can identify an HTMT document from the first kilobyte without building a DOM —
  the role `WEBVTT` plays for VTT. Fields after the version are `key=value` pairs,
  space-separated, order-insignificant, and open for extension; unknown keys are ignored.
- `data-htmt="1.0"` on the root element is **required**. It is the normative version
  declaration and the one a DOM-based validator or viewer reads. `document.documentElement.dataset.htmt`
  is the conformance test.

A file carrying the doctype and `data-htmt` is an HTMT document even if the comment is
absent. A file carrying the comment but not `data-htmt` is not.

### 3.2 Extension and media type

| Property | Value |
|---|---|
| Extension | `.htmt` (alternate: `.htmt.html` for zero-configuration hosting) |
| Media type served | `text/html; charset=utf-8` |
| Proposed alias | `text/htmt` — registered for identification, **never required**; a server sending it must expect browsers to download rather than render |
| Encoding | UTF-8, required, declared via `<meta charset="utf-8">` |

`text/html` is normative because it is what makes the format work. The spec ships the
one-line server configuration for both nginx and Apache, and documents that opening a
`.htmt` from a local filesystem may require a one-time "open with" association on some
platforms — which is precisely why `.htmt.html` exists as a sanctioned alternative for
people sharing files by email or chat.

## 4. Vocabulary

HTMT elements are custom elements in the `htmt-` namespace. Browsers parse unknown
elements as inert inline containers, style them freely via CSS, and never hide their
contents — which is what makes the no-JS fallback work by construction.

### 4.1 Module model

The draft's module system carries over, plus one new module:

| Module | Elements | Status |
|---|---|---|
| **Core** | `htmt-transcript`, `htmt-participants`, `htmt-person`, `htmt-agent`, `htmt-turn` | Required |
| **Temporal** | `start`, `end`, `t`, `duration` attributes; `htmt-event` | Optional |
| **Semantic** | `htmt-question`, `htmt-answer`, `htmt-decision`, `htmt-action`, `htmt-claim`, `htmt-fact`, `htmt-risk`, `htmt-note`, `htmt-quote` | Optional |
| **HyperText** | native `<a href>`, fragment-addressed cross-transcript references | Optional |
| **Media** | `htmt-media` wrapping native `<video>` / `<audio>` | Optional |
| **Vision** | `htmt-moment` — *new in 1.0* | Optional |
| **Extension** | `x-`-prefixed elements and attributes | Optional |

A minimal conforming document is the signature plus one `htmt-transcript` containing
`htmt-turn` elements. Everything else is additive.

### 4.2 Core structure

```html
<!doctype html>
<!-- HTMT/1.0 mode=directory moments=3 duration=00:18:42 -->
<html lang="en" data-htmt="1.0">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Engineering Standup — 2026-08-27</title>
  <style>/* htmt.css, inlined */</style>
</head>
<body>
<htmt-transcript id="standup-2026-08-27"
                 title="Engineering Standup"
                 date="2026-08-27"
                 duration="00:18:42">

  <htmt-participants>
    <htmt-person id="logan" name="Logan Schmidt"></htmt-person>
    <htmt-person id="nate"  name="Nate Waddell"></htmt-person>
    <htmt-agent  id="assistant" name="Assistant" model="claude-opus-5"></htmt-agent>
  </htmt-participants>

  <htmt-media id="recording" kind="video">
    <video controls preload="none" src="./standup.mp4"></video>
  </htmt-media>

  <htmt-topic id="inventory" name="Inventory">
    <htmt-turn id="t1" speaker="logan" start="00:00:03" end="00:00:07">
      Morning everyone. Let's start with inventory.
    </htmt-turn>
    <!-- remaining turns, moments, and events elided -->
  </htmt-topic>

</htmt-transcript>
<script>/* htmt.js, inlined */</script>
</body>
</html>
```

`speaker` resolves against a declared `htmt-person`/`htmt-agent` `id` when
`htmt-participants` is present; a literal name is permitted when it is not.

### 4.3 Turns and semantics

```html
<htmt-turn id="t42" speaker="logan" start="00:13:42.220" end="00:13:49.810">
  We should verify the export before billing runs.
  <htmt-action id="a1" owner="logan" due="2026-08-27" status="open">
    Validate the billing export.
  </htmt-action>
</htmt-turn>

<htmt-turn id="t43" speaker="john" start="00:13:51">
  <htmt-answer to="q17">I'll validate it this afternoon.</htmt-answer>
  <htmt-decision id="d1" status="accepted">
    Validate the export before the billing run.
  </htmt-decision>
</htmt-turn>
```

Semantic elements annotate text; they never replace it. A processor that understands
none of them still displays every word, because the words are text nodes in the
document flow.

**Timestamps.** `HH:MM:SS[.mmm]` for media-relative time (the common case);
ISO 8601 where a wall-clock instant is required. `start` may appear without `end`.
Turns are **not** assumed non-overlapping, and source order is preserved regardless of
timestamps — a normative rule inherited from the draft, because real meetings have
people talking over each other.

### 4.4 HyperText — native anchors, not a custom element

The draft's `<ref>` element becomes a plain `<a href>`. Cross-transcript references use
fragment addressing, which browsers resolve natively with no runtime:

```html
<a href="https://example.com/spec">Inventory Specification</a>
<a href="./billing.htmt#t184">Earlier billing discussion</a>
<a href="#m3">the chart Logan showed</a>
```

Every element with an `id` is therefore a durable, linkable address — turns, moments,
decisions, actions. `meeting.htmt#m3` opens a browser directly to a moment, with or
without JavaScript. This is a strict improvement over a custom `<ref>` element, which
would have required a script to be clickable at all.

## 5. The Vision module: `htmt-moment`

This is the element the format exists for.

```html
<htmt-turn id="t42" speaker="logan" start="00:13:42.220">
  Look at this chart — revenue dipped right here.

  <htmt-moment id="m3"
               t="00:13:44.500"
               kind="pointing"
               confidence="0.91"
               window="00:13:41.000/00:13:49.000">
    <figure>
      <img src="frames/m3.webp"
           width="1280" height="720" loading="lazy"
           alt="Line chart of monthly revenue for 2026 with a pronounced dip in Q3">
      <figcaption>The revenue chart — Q3 dip</figcaption>
    </figure>
  </htmt-moment>
</htmt-turn>
```

### 5.1 Attributes

| Attribute | Required | Meaning |
|---|---|---|
| `id` | Recommended | Fragment address; required for deck navigation and deep links |
| `t` | **Required** | Media-relative timestamp of the captured frame |
| `kind` | Recommended | `pointing` · `showing` · `screen` · `writing` · `gesture`; extensible via `x-` values |
| `confidence` | Optional | `0`–`1`, the vision pass's verdict that something is genuinely being shown |
| `window` | Optional | `start/end` search window the frame was selected from — makes re-extraction reproducible |
| `speaker` | Optional | Overrides the enclosing turn's speaker when a different person is doing the showing |

### 5.2 Content model — normative

A `htmt-moment` **must** contain a `<figure>` holding exactly one `<img>` (or one
`<video>` with a `poster`), and **should** contain a `<figcaption>` naming the referent.
The `<img>` **must** carry non-empty `alt` text and **should** carry `width`/`height`
to prevent layout shift.

The image is a real element in the document flow, not an attribute. This single decision
delivers three requirements at once: the no-JS fallback renders images inline where they
occurred; single-file mode is the same markup with a `data:` URI; and screen readers,
search indexers, and `Ctrl-F` all work with no cooperation from HTMT-aware software.

### 5.3 Optional clips

```html
<htmt-moment id="m7" t="00:31:02" kind="showing">
  <figure>
    <video controls preload="none" poster="frames/m7.webp"
           src="clips/m7.webm" width="1280" height="720"></video>
    <figcaption>Scrolling through the failing job queue</figcaption>
  </figure>
</htmt-moment>
```

Clips are external references by default. Base64-embedding a clip is permitted and
**discouraged** — the validator emits a size warning, because a handful of clips
defeats the entire size argument for the format.

## 6. Viewer runtime

Two canonical assets, versioned alongside the spec, with zero dependencies:

- **`htmt.css`** (~2 KB) — typography, speaker layout, figure treatment, deck chrome,
  light/dark via `prefers-color-scheme`, and a print stylesheet that drops the deck.
- **`htmt.js`** (~5 KB) — one IIFE, no framework, no build requirement.

Both are inlined into generated files (**mandatory** in single-file mode). Both are
optional per spec: a hand-written `.htmt` with neither is fully conforming.

### 6.1 The moment deck

```
┌─────────────────────────┬──────────────────────┐
│ transcript (scrolls)    │   [ frame image ]    │
│ logan  00:13:42         │                      │
│   Look at this chart —  │   00:13:44 pointing  │
│   revenue dipped here. ◀┼─▶ "The revenue chart │
│ nate   00:13:51         │      — Q3 dip"       │
│   Yeah, that dip is…    │   ◂  3 / 12  ▸       │
└─────────────────────────┴──────────────────────┘
```

- Next/prev buttons and <kbd>←</kbd>/<kbd>→</kbd> page through moments; the transcript
  scrolls to the owning turn and highlights it.
- Clicking an inline figure focuses that moment in the deck.
- Scroll-spy updates the deck as the reader scrolls the transcript.
- The deck collapses below the transcript on narrow viewports.

### 6.2 Normative runtime rules

1. **The viewer only enhances.** It must never remove, hide, or relocate transcript
   content out of the document flow. JS-on and JS-off must present the same information;
   only the navigation affordances differ. (Inline figures may be visually de-emphasised
   when the deck is active — not removed.)
2. **Deep links work without JS.** Moment ids are real fragments.
3. **No network access.** The viewer fetches nothing. A `.htmt` file opened offline,
   from a USB stick, or from an email attachment behaves identically.

## 7. Packaging modes

Identical markup; two ways to carry the pixels.

**Directory mode** — for archives, repos, and anything version-controlled:

```
standup-2026-08-27/
  standup.htmt
  frames/       m1.webp  m2.webp  m3.webp …
  clips/        m7.webm                      (optional)
  standup.mp4                                (optional source)
```

**Single-file mode** — for email, chat, and handoff: `img src` becomes
`data:image/webp;base64,…`, CSS and JS are inlined, and the file has **zero** external
references. The validator enforces that literally.

`htmt pack` and `htmt unpack` convert between modes losslessly and idempotently.

### 7.1 Size budget

The efficiency claim, quantified — this belongs in the spec because it is the format's
reason to exist:

| | Typical |
|---|---|
| One 1280px WebP frame, quality 80 | 40–80 KB |
| 20 moments, base64 (+33% overhead) | ~1.1–2.1 MB |
| Transcript text, 1 hour of speech | 60–90 KB |
| Inlined `htmt.css` + `htmt.js` | ~7 KB |
| **Self-contained 1-hour meeting** | **~1–2 MB** |
| Source video for comparison | ~1 GB |

Roughly a 500–1000× reduction while keeping every word and every moment that mattered.

## 8. AI pipeline — `htmt make`

```bash
npx htmt make meeting.mp4 --transcript meeting.vtt --single-file -o meeting.htmt
npx htmt make meeting.mp4 --whisper            # transcribe first, then proceed
```

### Stage 1 — Ingest
Parse SRT, VTT, plain text, or Whisper JSON into an internal turn model. Speaker
labels are read from `NAME:` prefixes or Whisper diarization when present. With
`--whisper`, shell out to a local whisper CLI first. Transcription is **delegated,
never bundled** — the pipeline's job is moments, not ASR.

### Stage 2 — Deixis detection (text)
`claude-opus-5`, structured output, transcript chunked with overlap so a candidate is
never split across a boundary. The model returns candidates:

```json
{
  "quote": "Look at this chart — revenue dipped right here.",
  "turnId": "t42",
  "window": "00:13:41.000/00:13:49.000",
  "kindGuess": "pointing",
  "referentGuess": "a revenue chart",
  "textConfidence": 0.88
}
```

Cheap, high-recall, deliberately over-inclusive. Precision is Stage 4's job.

### Stage 3 — Frame harvest
ffmpeg extracts 3–5 candidate frames spread across each window, downscaled to 1280px
wide. One ffmpeg invocation per window; windows are processed concurrently with a
bounded worker pool.

### Stage 4 — Vision verification
`claude-opus-5` receives the candidate frames plus the surrounding transcript and
decides, per candidate:

- Is something genuinely being shown, or is this figurative language? *(reject path)*
- Which frame is the best representative — sharpest, most complete, least mid-transition?
- What is the referent, in a caption a reader can scan?
- What is the `alt` text?
- What `kind` is it, and with what `confidence`?

Rejected candidates are dropped with a logged reason. This stage is why the format's
images can be trusted, and it is the single biggest quality differentiator against a
naive "grab a frame at the timestamp" implementation.

### Stage 5 — Emit and verify
Serialize to `.htmt` (directory or packed), then **run the validator automatically**
and fail the command if the output does not conform. A generator that can emit invalid
files is a generator that will.

### 8.1 Model integration

A provider-pluggable `LlmClient` interface with the Anthropic SDK
(`@anthropic-ai/sdk`) as the reference implementation:

- Model `claude-opus-5`; adaptive thinking (`thinking: { type: "adaptive" }`).
- Streaming for the long transcript passes.
- Server-side fallbacks enabled by default
  (`betas: ["server-side-fallback-2026-07-01"]`, `fallbacks: "default"`), and
  `stop_reason: "refusal"` handled explicitly rather than assumed away.
- Structured outputs via `output_config.format` for both model stages.
- Prompt caching on the stable system prompt across chunked requests.

`ANTHROPIC_API_KEY` is read from the environment; the CLI never writes credentials
to disk or into output files.

### 8.2 Auditability

Every run writes a decision log — candidates found, frames harvested, verdicts,
rejection reasons, token usage. `--explain` prints it. An AI pipeline that silently
drops content must be able to show its work.

## 9. Validator and converters

### 9.1 `htmt check`

Library plus CLI, built on a real HTML parser (`parse5`) rather than regex. Checks:

| Check | Severity |
|---|---|
| Doctype present and correct; `data-htmt` version declared | error |
| Exactly one `htmt-transcript` root | error |
| `id` values unique within the document | error |
| `to` / `href` fragment references resolve to a local `id` | error |
| Timestamp syntax valid; `end` ≥ `start`; `t` within any declared `window` | error |
| Every `htmt-moment` contains a `figure` with an `img`/`video` | error |
| Every moment image has non-empty `alt` | error |
| Single-file mode contains zero external references | error |
| Turn `start` values non-monotonic | warning |
| Base64-embedded video, or file over 10 MB | warning |
| Moment missing `id`, `kind`, or `figcaption` | warning |

CI-friendly exit codes: `0` clean, `1` errors, `2` warnings-only under `--strict`.

### 9.2 Conformance corpus

`fixtures/` holds valid documents (minimal, full, single-file, overlapping speech,
agent participants) and deliberately broken ones, each paired with expected validator
output. It is simultaneously the validator's test suite and **the public conformance
suite** any third-party HTMT implementation can run against. Shipping this is what
separates a standard from a file format one project happens to use.

### 9.3 Subtitle converters

```bash
npx htmt from-srt lecture.srt -o lecture.htmt
npx htmt from-vtt lecture.vtt --media ./lecture.mp4
```

No AI, no video processing — cues become turns, `NAME:` prefixes become speakers,
adjacent cues from one speaker within a gap threshold merge into single turns.
The zero-cost on-ramp: anyone with a caption file gets a valid `.htmt` in one command
and can add moments later.

## 10. Repository and project shape

npm workspaces monorepo:

```
htmt/
  spec/            # the specification, published as a styled HTML page
  packages/
    core/          # parse, serialize, pack/unpack, types — shared by all
    viewer/        # htmt.css + htmt.js, built and versioned
    cli/           # the `htmt` binary: make, pack, unpack, check, from-srt, from-vtt
  examples/        # real .htmt files, both packaging modes
  fixtures/        # conformance corpus
```

`core` is the dependency all others share, so parsing and serialization have exactly
one implementation.

**Licensing.** MIT for code; CC BY 4.0 for the specification text — the standard
combination for a spec meant to be re-implemented.

**Versioning.** The format version (`HTMT/1.0`) moves independently of package
versions. Minor format versions are strictly additive: a 1.1 document must remain
readable by a 1.0 processor, with unknown elements preserving their text.

**Roadmap, explicitly out of scope for 1.0:** clip-first workflows, media-seek
integration binding the deck to a `<video>` element, chapter/summary decks, JSON-LD
export, cryptographic provenance signing, live-capture integrations. Published as a
roadmap so contributors see the direction without 1.0 absorbing it.

## 11. Testing strategy

| Layer | Approach |
|---|---|
| `core` | Round-trip property tests: parse → serialize → parse is stable; pack → unpack → pack is byte-identical |
| `check` | The conformance corpus — every fixture asserts exact diagnostics |
| `viewer` | Vitest + jsdom for deck logic; one Playwright smoke test asserting the no-JS fallback renders every moment image |
| `cli` | Command-level tests against fixture videos (a few seconds, committed) |
| Pipeline | **Record/replay LLM fixtures** so CI never needs an API key; one live smoke test behind an env flag |

Recorded fixtures matter more than usual here: a pipeline whose tests require paid API
calls is a pipeline contributors cannot run, and an open standard lives or dies on
whether outsiders can contribute.

## 12. Error handling

- **Input validation at the boundary.** Transcript and video inputs are validated
  before any model call; malformed timestamps and unreadable media fail immediately
  with actionable messages.
- **Fail fast on bad input; degrade gracefully mid-run.** A single moment failing
  vision verification (API error, undecodable frame) drops that moment with a warning
  and the run continues. Losing 1 of 12 moments must not lose the other 11.
- **Never silently swallow.** Every drop is logged with a reason and surfaced in the
  run summary.
- **Refusals handled explicitly.** `stop_reason: "refusal"` is checked before reading
  content, with server-side fallbacks configured.
- **Generated output is validated before the command exits.**

## 13. Security and privacy

Transcripts carry sensitive material by nature. The draft's rules carry over, with
additions the HTML5 substrate makes necessary:

1. **Escape everything.** All transcript text is HTML-escaped on serialization.
   A meeting where someone says "less than script greater than" must not produce a file
   that executes it. This is the single most important rule in the format, because the
   substrate is executable.
2. **Generated files contain only the canonical viewer script.** `htmt check` flags any
   other `<script>`, any inline event-handler attribute, and any `javascript:` URL in a
   file it is asked to verify — an HTMT file received from a third party is untrusted
   input, and the validator is how you find out what is in it.
3. **The viewer makes no network requests**, so opening a file cannot phone home.
4. **Metadata is a claim, not proof.** Speaker identity, model attribution, and
   confidence scores are assertions by whoever generated the file. Provenance signing
   is roadmap, not 1.0 — and the spec says so plainly rather than implying trust.
5. **Redaction must be independently possible.** Text, frames, participants, and
   timestamps are separable, so a redaction tool can strip frames while keeping the
   transcript, or strip identities while keeping the content.
6. **No credentials in output.** The pipeline never writes API keys, file paths outside
   the output directory, or environment data into generated documents.

## 14. Comparison to existing formats

| Format | Answers | HTMT adds |
|---|---|---|
| TXT | What was said? | Speakers, time, semantics, imagery |
| SRT / VTT | What caption, when? | Discourse structure, meaning, and the frames themselves |
| HTML | How is a document structured? | A conversation timeline as the native model |
| JSON exports | How does one vendor serialize? | A portable, human-readable interchange format that opens in a browser |
| Video | Everything, opaquely | The 0.1% that mattered, addressable and searchable |

> SRT/VTT: *"What was said, and when?"*
> HTMT: *"Who said what, when, in response to what, what did it mean, what was decided —
> and what were they pointing at?"*

## 15. Deliverables for the implementation plan

1. `packages/core` — types, parser, serializer, pack/unpack.
2. `packages/viewer` — `htmt.css`, `htmt.js`, the deck.
3. `packages/cli` — `check`, `from-srt`/`from-vtt`, `pack`/`unpack`, `make`.
4. `fixtures/` — the conformance corpus.
5. `spec/` — the specification document, itself served as an HTML page.
6. `examples/` — at least one real generated meeting in both packaging modes.

Suggested build order: `core` → `check` + fixtures → `viewer` → `from-srt/vtt`
→ `pack/unpack` → `make`. Each step produces something demonstrable on its own, and
`make` — the most expensive piece — lands last, on top of a validated foundation.
