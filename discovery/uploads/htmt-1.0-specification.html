Technical Specification · Draft 1.0

HTMT

HyperText Markup Transcript is a human-readable, machine-readable markup language for representing conversations as structured, temporal, semantically meaningful documents.

Core definition: HTMT is a serialization format for conversations. It represents not only what was said, but who said it, when it occurred, what it meant, how it relates to surrounding discourse, and what actions, decisions, references, or events emerged from it.

1. Purpose and Scope

HTML describes documents. HTMT describes conversations over time.

HTMT is intended for meeting transcripts, support sessions, interviews, podcasts, recorded calls, AI conversations, hearings, collaborative work sessions, video transcripts, and other forms of dialogic or event-driven communication.

Unlike plain text, subtitle formats, or presentation-oriented transcript exports, HTMT preserves the structure and semantics of a conversation in a form that remains readable without specialized software.

Human-readable

A valid HTMT file should be understandable in a text editor without requiring a parser.

Machine-readable

Applications may extract speakers, timestamps, actions, decisions, topics, references, claims, and other semantic structures.

Temporal

Speech and events may be mapped to source audio or video with optional start and end times.

Semantic

The format may encode the role or consequence of an utterance rather than only its literal wording.

2. Design Principles

  1. Conversation-first. Speaker turns are the primary unit of discourse.
  2. Semantics over presentation. HTMT describes meaning and structure; rendering is implementation-defined.
  3. Progressive complexity. A minimal transcript requires only a root and turns. Timestamps, semantics, media, and metadata remain optional.
  4. Graceful degradation. Unknown semantic elements should preserve their contained text.
  5. Extensibility. Domain-specific semantics must not require expansion of the core standard.
  6. Stable identity. Significant turns and semantic objects may carry identifiers for durable cross-references.
  7. Transport independence. HTMT is a file/document format, not a network protocol.
  8. AI-native without being AI-dependent. The language supports humans, software agents, and model-generated discourse equally.

3. Document Syntax

HTMT uses an XML-like markup syntax encoded as UTF-8. Element and attribute names are case-sensitive and should use lowercase ASCII names in the core specification.

3.1 Minimum valid document

<!HTMT 1.0>

<transcript>
  <turn speaker="Logan">
    Did the deployment finish?
  </turn>

  <turn speaker="Nate">
    Yes.
  </turn>
</transcript>

3.2 Recommended document structure

<!HTMT 1.0>

<transcript
  id="standup-2026-08-27"
  title="Engineering Standup"
  date="2026-08-27"
  duration="00:18:42"
  lang="en">

  <meta>...</meta>
  <participants>...</participants>
  <media>...</media>
  <body>...</body>

</transcript>
Normative intent: An HTMT processor should preserve text contained inside elements it does not understand. Unknown semantic markup must not cause otherwise readable transcript content to disappear.

4.1 Participants

<participants>
  <person id="logan" name="Logan Schmidt" />
  <person id="nate" name="Nate Waddell" />
  <agent id="assistant" name="Assistant" model="ExampleModel" />
</participants>

A speaker attribute on a turn should resolve to a participant id when participant declarations are present. Implementations may permit literal speaker names when no participant registry is declared.

5. Temporal Model

Timestamps are optional. This allows the same syntax to represent a live meeting, a typed chat, a podcast, or an asynchronous AI conversation.

5.1 Timed turn

<turn
  id="t42"
  speaker="logan"
  start="00:13:42.220"
  end="00:13:49.810">
  We should verify the export before billing runs.
</turn>

5.2 Time representation

  • Relative media time should use HH:MM:SS with optional fractional seconds.
  • Absolute time may use ISO 8601 where a real-world timestamp is required.
  • start may appear without end.
  • Processors should not assume turns are non-overlapping.
  • Overlapping speech should be representable without altering source order.

6. Semantic Model

Semantic elements allow transcript text to carry operational or interpretive meaning. They are annotations on discourse, not replacements for the underlying words.

ElementMeaningTypical attributes
<question>A question posed by a participant.id
<answer>An answer or response.to
<decision>A proposed, accepted, superseded, or rejected decision.id, status
<action>An assigned or inferred action item.id, owner, due, status
<claim>A factual or inferential claim.confidence, source
<fact>A statement asserted as established within the transcript context.source
<risk>A risk, concern, or possible adverse condition.severity
<note>An editorial or system annotation.author, type
<quote>Quoted material distinct from the current speaker's own utterance.source

6.1 Question and answer relationship

<turn speaker="john" start="00:08:31">
  <question id="q17">
    Who is going to validate the export?
  </question>
</turn>

<turn speaker="logan" start="00:08:45">
  <answer to="q17">
    I'll validate it this afternoon.
  </answer>

  <action owner="logan" due="2026-08-27" status="open">
    Validate export.
  </action>
</turn>

6.2 Decision annotation

<turn speaker="logan">
  I think we should deploy this Friday.

  <decision id="d4" status="proposed">
    Deploy Friday.
  </decision>
</turn>

7. HyperText References

The “HyperText” portion of HTMT is normative to the design: transcripts should be able to link to resources, identifiers, other transcripts, and exact transcript locations.

<ref href="https://example.com/spec">
  Inventory Specification
</ref>

<ref href="jira://FFS-2309">
  FFS-2309
</ref>

<ref transcript="billing.htmt" turn="t184">
  Earlier billing discussion
</ref>

References may target URLs, application-specific URI schemes, local files, transcript identifiers, turn identifiers, semantic object identifiers, or other resolvable resources.

8. Events and Media

HTMT models more than spoken language. Events allow software to preserve important contextual occurrences that happen on the timeline.

<event type="silence" start="00:02:14" duration="3.2s" />

<event type="laughter" start="00:03:02" />

<event type="screen-share" start="00:08:11">
  Inventory Dashboard
</event>

<event type="file-shared">
  <ref href="./inventory-report.xlsx">
    Inventory Report
  </ref>
</event>

8.1 Media association

<media
  id="recording"
  type="video"
  src="./meeting.mp4"
  duration="00:18:42" />

A transcript viewer may use temporal attributes to seek media when a user selects a turn or semantic object.

9. Topics and Hierarchical Structure

Topics may divide a transcript into semantic sections while retaining the chronological sequence.

<topic id="inventory" name="Inventory">
  <turn speaker="john">
    Let's talk about inventory drift.
  </turn>
  ...
</topic>

<topic id="billing" name="Billing">
  ...
</topic>

A renderer can derive navigable chapter markers, summaries, indexes, or topic timelines directly from these structures.

10. AI and Software-Agent Conversations

HTMT intentionally treats software agents as first-class participants rather than forcing them into human speaker models.

<participants>
  <person id="user" name="Logan" />
  <agent
    id="assistant"
    name="Assistant"
    model="ExampleModel"
    provider="ExampleProvider" />
</participants>

<body>
  <turn speaker="user">
    Explain why our inventory numbers drift.
  </turn>

  <turn speaker="assistant">
    There are several possible causes.

    <claim confidence="0.82">
      Timing differences between systems may contribute to observed drift.
    </claim>
  </turn>
</body>

Model, provider, tool, runtime, or generation metadata may be represented when needed, but implementations should avoid treating such metadata as mandatory for basic transcript portability.

11. Extensibility

The HTMT core should remain intentionally small. Domain vocabularies should be introduced through namespaced extension elements.

<x-medical:diagnosis>
  ...
</x-medical:diagnosis>

<x-sales:opportunity>
  ...
</x-sales:opportunity>

<x-support:ticket>
  ...
</x-support:ticket>

11.1 Extension requirements

  • Extension elements should use a namespace-like prefix.
  • Core processors may ignore unknown extension semantics.
  • Unknown extensions must not make the transcript unreadable.
  • Extensions should preserve meaningful text content where practical.
  • Extensions should not redefine the semantics of core elements.

12. Conformance Model

A conforming HTMT 1.0 document should satisfy the following requirements:

  1. Be encoded as UTF-8.
  2. Contain exactly one root <transcript> element.
  3. Represent conversational contributions using <turn>.
  4. Use unique values for identifiers within the document where id is present.
  5. Resolve internal to, turn, and comparable identifier references when targets are local.
  6. Preserve source ordering of turns and events.
  7. Use valid timestamp forms when temporal attributes are present.

12.1 Processor behavior

A basic processor may display only turn text and speakers. An advanced processor may additionally resolve links, seek media, construct topic navigation, identify action items, visualize decisions, trace question-answer pairs, or index semantic objects.

Compatibility rule: semantic richness should be additive. A sophisticated HTMT document must remain useful to a simple processor.

13. Security, Privacy, and Trust

Transcript data may contain sensitive personal, organizational, legal, or operational information. The file format itself does not imply that embedded metadata is trusted.

  • Processors should treat external references as untrusted input.
  • Automatic execution of linked scripts, binaries, or application URIs is discouraged.
  • Renderers should escape transcript text and extension content before inserting it into HTML or other executable environments.
  • Metadata such as speaker identity, model identity, authorship, confidence, and semantic annotations should be treated as claims unless cryptographically verified.
  • Redaction tools should be able to remove text, metadata, participant identifiers, temporal information, references, and semantic annotations independently.

14. Relationship to Existing Formats

FormatPrimary question answeredHTMT distinction
TXTWhat text exists?HTMT adds participant, temporal, semantic, and relational structure.
SRTWhat caption appeared, and when?HTMT represents discourse and meaning, not only subtitle timing.
WebVTTWhat timed text cues belong to media?HTMT adds conversation identities, semantic objects, topics, actions, and hypertext relationships.
HTMLHow is a document structured and presented?HTMT's native model is a conversation timeline rather than a page document.
JSON transcript exportsHow can one application's transcript data be serialized?HTMT targets a portable, human-readable interchange syntax with shared semantic primitives.
Conceptual distinction:
SRT/WebVTT: “What was said, and when?”
HTMT: “Who said what, when, in response to what, what did it mean, what was decided, and what does it connect to?”

15. Complete Example

<!HTMT 1.0>

<transcript
  id="engineering-standup-2026-08-27"
  title="Engineering Standup"
  date="2026-08-27"
  duration="00:18:42"
  lang="en">

  <participants>
    <person id="logan" name="Logan Schmidt" />
    <person id="nate" name="Nate Waddell" />
    <person id="john" name="John Martin" />
  </participants>

  <media
    id="recording"
    type="audio"
    src="./engineering-standup.mp3"
    duration="00:18:42" />

  <body>

    <topic id="inventory" name="Inventory">

      <turn id="t1" speaker="logan" start="00:00:03">
        Morning everyone. Let's start with inventory.
      </turn>

      <turn id="t2" speaker="nate" start="00:00:08">
        The reconciliation job completed overnight.
      </turn>

      <turn id="t3" speaker="john" start="00:00:14">
        <question id="q1">
          Are all ShipStation deductions represented in our system?
        </question>
      </turn>

      <turn id="t4" speaker="nate" start="00:00:20">
        <answer to="q1">
          Yes, for the pathways we've currently validated.
        </answer>
      </turn>

      <turn id="t5" speaker="logan" start="00:01:02">
        We should verify the export before billing runs.

        <action
          id="a1"
          owner="logan"
          due="2026-08-27"
          status="open">
          Validate the billing export.
        </action>
      </turn>

      <turn id="t6" speaker="john" start="00:01:18">
        Agreed.

        <decision id="d1" status="accepted">
          Validate the export before the billing run.
        </decision>
      </turn>

    </topic>

    <event type="screen-share" start="00:02:11">
      <ref href="https://example.com/inventory">
        Inventory Dashboard
      </ref>
    </event>

  </body>
</transcript>

16. Proposed HTMT 1.0 Module Model

For standardization, HTMT may be defined as a small mandatory core with optional capability modules.

HTMT Core

transcript, body, participants, person, agent, turn, meta.

Temporal Module

Timing, durations, overlap, event sequencing, media synchronization.

Semantic Module

Questions, answers, decisions, actions, facts, claims, risks, notes, quotations.

HyperText Module

External links, transcript-to-transcript references, turn references, application URIs.

Media Module

Audio/video association, screen sharing, attachments, timed non-speech events.

Extension Module

Namespaced domain vocabularies while preserving forward compatibility.

16.1 Design summary

HTML Document → Elements → Meaning → Presentation

HTMT Conversation → Turns → Meaning → Timeline

Specification thesis: HTMT should not become a giant transcription schema. Its core value is a small, durable conversation model that remains readable by people, useful to conventional software, and structurally rich enough for AI-era communication.
